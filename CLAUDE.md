# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A Python package (`royal_navy_ships/`) that queries the public Wikidata and DBpedia SPARQL endpoints for Royal Navy sailing ships and generates a canonical, gitignored `ships.json` dataset (published via GitHub Releases, not tracked in git history). There is still no build system. Run the pipeline via `python3 -m royal_navy_ships.pipeline` from the repo root, and the tests via `python3 -m unittest discover` (stdlib `unittest`, no network, no third-party test runner -- the zero-dependency rule covers test code too).

## Data pipeline

- **`royal_navy_ships/model.py`** — canonical `Ship`/`ShipName`/`ShipEvent` dataclasses shared by all source adapters. A ship's name is a time-qualified list (`names`), not a single field, since ships were often renamed; `start_year`/`end_year`/`end_reason`/`end_reason_source` are derived properties, not stored fields -- from the event timeline, falling back to the `fate` string -- and `to_dict` adds them to the serialized output by hand.
- **`royal_navy_ships/sources/sparql.py` and `royal_navy_ships/cache.py`** — shared plumbing every adapter uses: a SPARQL-over-HTTP client with retry, and raw-result load/save/canonicalize. Adapters never write their own cache; `pipeline.py` commits caches only after the dataset write succeeds.
- **`royal_navy_ships/sources/wikidata.py`** — the primary source adapter, producing the ship list itself. Queries Wikidata's public SPARQL endpoint live for Royal Navy ships in the sailing-ship rating classes (first-rate through sixth-rate, sloop-of-war, gun-brig -- see `RATING_CLASS_QIDS`), not a hardcoded date range. `in_sailing_era` then drops post-1860 vessels from the two classes Wikidata does not era-bound (`ERA_LIMITED_RATINGS`); rated ships are never era-filtered. `fetch_ships()` compares the freshly-fetched result against the cache at `.cache/wikidata_raw.json` (gitignored) and reports whether it changed, but does not save the cache itself.
- **`royal_navy_ships/sources/dbpedia.py`** — enrichment adapter. Joins DBpedia resources to ships via `owl:sameAs` on the Wikidata QID each record already carries (never by name), and merges Wikipedia infobox fields -- armament, tonnage, length, beam, complement, sail plan, builder, fate -- through `Ship.set_field`. Caches at `.cache/dbpedia_raw.json`, same contract as above.
- **`royal_navy_ships/pipeline.py`** — CLI entry point. Run via `python3 -m royal_navy_ships.pipeline` from the repo root. Writes `ships.json` (gitignored -- the dataset is published via GitHub Releases, not tracked in git history) atomically, then commits the new cache -- in that order, so a failed/killed output write never leaves a cache that falsely claims the output is current. Skips regeneration if nothing changed since the last run.

No third-party dependencies -- the SPARQL client uses `urllib.request` from the standard library.

Every source adapter has the same shape: build query -> fetch rows -> parse/clean -> merge into canonical `Ship` records via `set_field`. Adding a source means writing one adapter and calling it from `pipeline.py`.

## Key gotchas

- **Wikidata's armament data (`P520`/`P1114`) is very sparse.** `Ship.guns` is frequently `None`; where present, treat it as best-effort, not authoritative -- it was found during design to undercount even well-documented ships like HMS Victory.
- **Wikidata's `sloop-of-war` class is not era-bounded.** `Q928235` tags 1790s sailing sloops and 1915 Acacia-class convoy escorts identically -- there is no narrower QID to swap in, so the era constraint in `in_sailing_era` is the only thing keeping 20th-century vessels out. Filtering happens after the fetch, deliberately: the cache holds the raw candidate set so `changed` reflects the endpoint, not the cutoff.
- **A ship can carry several rating-class `P31` statements, and the highest rate wins.** About 10 do, typically from reclassification mid-career. `RATING_PRIORITY` in `wikidata.py` declares the order (First..Sixth, then Sloop, then Gun-brig) and `parse_candidates` consults it. This is declared separately from `RATING_CLASS_QIDS` on purpose: the two happen to be in the same order today, so deriving priority from insertion order would work and would then silently change the policy the moment either dict were reordered. Before this, first-row-wins combined with JSON-sorted canonicalization meant the lexicographically smallest class URI won, so Gun-brig (`Q130396697`) beat every `Q89xxxx` rate class.
- **`end_year`/`end_reason` read the Wikidata timeline first and fall back to parsing `fate`.** The timeline path is gated on `FINAL_EVENT_LABELS` -- it reports only when the *last dated* event actually ends a vessel -- and that is 35 ships out of 2,097. Before the gate the last dated event was returned unconditionally, so 1,573 ships reported `end_reason == "ship launching"` with `end_year == start_year`, reading as though they were lost at launch. The gate made the properties honest and left them nearly empty; the `fate` fallback (#28) is what made them useful, taking `end_reason` to 906 ships. **A Wikidata terminal event beats `fate` where both exist** (18 ships) -- that is `SOURCE_PRIORITY` applied rather than an exception to it, so `_end()` is an ordinary fallback chain and not a per-field override bolted onto `set_field`. `end_reason_source` is what tells the two apart in the output, and they do not deserve equal confidence: 35 controlled-vocabulary events versus 871 parses of free text.
- **The `fate` parser reads the leading verb and nothing else.** `FATE_OUTCOMES` maps it onto a `FINAL_EVENT_LABELS` value so `end_reason` is one vocabulary whatever source it came from; `FATE_YEAR_RE` takes the *first* year in the string. Both choices are about the same failure: `fate` is one free-text sentence, and a terminal verb appearing later in it usually belongs to a different clause with a different date -- "Recaptured 1776 and sold, possibly in 1777" would otherwise report a disposal dated to the recapture. Verbs a ship survives (`captured`, `taken`, `hulked`, `decommissioned`) are absent for the same reason `capture` is absent from `FINAL_EVENT_LABELS`. So are `lost`, `abandoned`, `disappeared`, `condemned` and `presumed`: they are terminal in meaning, but every label in the vocabulary asserts a *manner* of ending, and choosing one would invent a detail the string withholds. That deliberate silence is why coverage is 906 and not the ~1,050 ships that have any `fate` at all.
- **`to_dict` is no longer just `asdict`.** `asdict` serializes fields only, so the four derived properties (`start_year`, `end_year`, `end_reason`, `end_reason_source`) are added by hand. Before #28 they were `@property` and therefore invisible in `ships.json` -- which is why nothing ever caught the pre-gate `end_reason == "ship launching"` bug, the same latency that hid the `start_year` skolem-IRI crash. A new derived property that is not added here repeats that. All four keys are always emitted, `None` included.
- **`end_year` is not cross-checked against `start_year`.** One ship (HMS *Camel*, `Q85765231`) reports `end_year` 1776 against a Wikidata launch of 1777. That is a genuine Wikidata/Wikipedia disagreement, and suppressing it would hide an upstream inconsistency behind a parser that looks more careful than it is.
- **`FINAL_EVENT_LABELS` matches Wikidata event *labels*, not QIDs.** A relabelling upstream silently drops an event out of the set. Matching QIDs would be more robust -- the events query already binds `?event` -- but `ShipEvent` carries no QID field, so it would mean a model change and a cache invalidation. Deliberately deferred.
- **A Wikidata "unknown value" date arrives as a skolem IRI, not a date.** 86 launch events carry `http://www.wikidata.org/.well-known/genid/...` in the P585 slot. `_event_date` maps those to `None`; before it existed, `Ship.start_year` raised `ValueError` on them -- latent only because nothing called the property.
- **A ship's `names` list is derived entirely from its Wikidata event timeline's `named_as` qualifiers** (`P1810` on `P793` significant-event statements), not from a separate name property. A ship with no tagged rename events gets a single `ShipName` from its current Wikidata label. Only *dated* naming events join the sequence -- an undated one has no knowable position, and `current_name` returns `names[-1]`, so placing it arbitrarily would make the current name arbitrary. `build_notes` records those in `notes` instead. Note this vocabulary is thin: only 4 ships in the current fleet carry any `named_as` qualifier at all (9 rows), and none is undated, so the undated path is a guard against future data rather than a fix to current output.
- **`SHIP_ID_NAMESPACE` in `model.py` must never change.** Ship ids are `uuid5(SHIP_ID_NAMESPACE, "wikidata:<QID>")`, not random, so that a ship keeps its `id` across releases. Editing the namespace constant, or reordering `ID_SOURCE_PRECEDENCE`, renumbers every ship in the dataset and silently breaks every consumer joining across versions. `tests/test_ship_id.py` pins both the namespace and a known ship's id as literals to catch exactly that. Appending a new system to the end of `ID_SOURCE_PRECEDENCE` is safe; only the first match is used.
- **`run_query`'s retry policy has three separate tracks, and `HTTPError` is why.** `urllib.error.HTTPError` subclasses `URLError`, so catching `URLError` catches every HTTP status too. `_is_permanent` therefore fails 4xx fast (except 408/429, which a retry can fix); `_retry_after_delay` handles 429/503 by honoring the server's `Retry-After` on its own budget (`rate_limit_retries`, default 5) so a busy endpoint can't exhaust the three ordinary attempts before the query is answered; everything else gets linear backoff. Truncated responses raise `IncompleteRead` (subclasses `HTTPException`, unrelated to `URLError`) or `ConnectionResetError` (a *sibling* of `URLError` under `OSError`) — both are in `RETRYABLE_EXCEPTIONS` explicitly because neither is reachable via `URLError`.
- **`notes` is composed before `set_field`, never appended after.** `set_field` gives the canonical slot to the first non-empty value, so a second `set_field("notes", ...)` call would be recorded as a *conflict* rather than extending the text. `to_ships` builds the full string via `build_notes` and sets it once.
- **Everything under `.cache/` and `ships.json` are gitignored.** Regenerate locally via `python3 -m royal_navy_ships.pipeline`; don't expect them in a fresh checkout.
- **Canonical fields answer the question, not "who said what".** `Ship.set_field` gives the canonical slot to the highest-priority source (`SOURCE_PRIORITY` in `model.py`, lower wins) and records disagreements in `conflicts`. Never assign a mergeable field directly -- go through `set_field` so provenance stays complete. Precedence is policy, not call order: a higher-priority value arriving late displaces the incumbent and demotes it into `conflicts`, so the adapters can run in any order. An adapter whose name is absent from `SOURCE_PRIORITY` ranks below every declared one -- add new sources to the map when wiring them up.
- **`field_sources[field]` is a list of concurring sources, not a single string.** A source repeating the canonical value is appended rather than dropped, and that is the only thing separating a same-source alternative (DBpedia's infobox listing two builders -- all 1090 conflict entries in the current dataset) from a real cross-source disagreement: compare a conflict entry's `source` against `field_sources[field]`. Consumers reading it as a string will break.
- **DBpedia values are raw Wikipedia infobox fragments and are frequently junk.** `dbp:shipFate` is a malformed `--MM-DD` date in roughly two thirds of cases; sail plans and builders arrive as resource URIs, not text. `clean_value` normalizes what it can and returns `None` for the rest -- junk must never reach a canonical field.
- **`Ship.guns` is only recoverable for roughly half of DBpedia-matched ships.** Armament is usually a per-deck breakdown; only a bare integer or an explicitly stated total is parsed. Summing the `24 × 9-pounder` multipliers is deliberately avoided because many entries span several eras or navies and would double-count.
- **There is no draught data in DBpedia** (`dbp:shipDraught`, `dbp:shipDraft`, `dbo:draft` are all empty for this fleet), despite the design spec listing the field.
